# Token 估算口径（3.0.6 起）

插件里所有 token 数字都是**估算**：DSH 进程里没有分词器，插件也不可能为每条文本调一次 provider 计数。这里记录估算用的密度表、它是怎么测出来的、以及误差有多大。

旧口径（≤3.0.5）是 `ASCII ÷ 4 + 非 ASCII ÷ 1.6`。它把中文估得很准，但把 JSON 结构符（`{ } [ ] " : ,`）按正文的四分之一价算，导致 JSON / 工具 schema 多的内容系统性低估；同时把英文正文估高了约 29%。

## 密度表

| 类别 | 包含 | tokens/字符 | 字符/token | 拟合残差 |
|---|---|---|---|---|
| `ascii_prose` | 字母、数字、空白、非 JSON 的 ASCII 标点 | 0.176 | 5.7 | ±4% |
| `json_struct` | `{` `}` `[` `]` `"` `:` `,` | 0.977 | 1.02 | ±1% |
| `cjk` | CJK 汉字、CJK 标点、全角、假名、谚文 | 0.609 | 1.64 | ±2% |
| `other_unicode` | emoji、符号、带音标拉丁字母 | 1.0 | ~1.0 | 样本仅 22 个码元，粗 |

实现见 `lib/measure.js`（`measureText()` 同时返回类别直方图，便于解释数字为什么大）。

## 怎么测的

- 环境：DSH 0.2.2-rc.5（Desktop/Windows），模型 `deepseek-flash`，隔离 profile（不碰用户实例）。
- 方法：每轮开一个干净会话；先发一条一行的基线消息，再按类别各发一条纯文本 payload，要求模型只回两个字；从会话日志 `assistant/message` 的 `usage` 里读 `inputTokens + cacheReadTokens`（provider 报的，不是本地估的）。
- 逐类密度 = 相邻两步 prompt 之差，减去拟合出的「每步固定开销」（约 25 token：上一条回复 + 每步宿主上下文）。
- 第一轮 6 条 payload 全是 4,200 字符——长度相同会让「ASCII」和「JSON」的系数共线、无法分开。所以补了第二轮 3,000 / 3,000 / 2,000 字符，把长度维度打开。
- 最小二乘，9 个观测、4 个未知数，最差残差 ±6.3%，多数 <2%。

## 和对外的交叉验证

上游 issue（deepseek-harness discussions #13906）给出的真实事故是「约 3.29M 字符 → provider 2,133,162 tokens」，即 0.648 tokens/字符。用上面的表，当内容里 JSON 结构符占 30–35%、中文 40–45%、正文 22% 时，模型给出 0.64–0.66 tokens/字符，与事故数字吻合。也就是说那 2.5 倍误差主要来自 JSON 结构符和中文，而不是「中文单独就 2.5 倍」。

测量与结论已发在上游讨论：<https://github.com/deepseek-ai/deepseek-harness/discussions/13906#discussioncomment-19811615>

## 误差与边界

- 这是**类别平均密度**，不是分词器结果；同一类内不同文本仍会漂移（英文散文、代码、数字串各不相同）。
- emoji / 符号样本太少（22 个码元），只能算占位值。
- 统计按 UTF-16 码元：一个 emoji 在 `other_unicode` 里记 2 个码元（与字符串长度一致）。
- 工具 schema 的结构符占比高，这类内容现在会明显变大——这是修正，不是回归。
- provider / 模型换了以后密度会变，需要重新按同样方法标定。
