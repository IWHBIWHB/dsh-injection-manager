# 性能

这份文档只回答一个问题：日常使用会不会卡。数字来自本机一份 355 条目、27 个套件、230 个 REA 条目的真实快照，以及 v2 表面的按需加载策略与接口实测；不是基准测试。

环境：Windows 11、Edge 当前版、视口 1200×860、数据来自本机 DSH 0.2.2-rc.3 的真实 `/summary`。

## 管理页（v1 基线，v2 不变）

| 指标 | 实测 |
| --- | --- |
| 页面 `domContentLoaded` | 68–89 ms |
| 首次内容绘制（FCP） | 88–112 ms |
| 面板可交互（套件行出现） | 240–310 ms |
| 分组视图行数 | 27 行（全部渲染） |
| 展开最大套件（230 行）到可见 | 61–120 ms |
| 搜索「rea」到结果稳定 | 37–54 ms |
| 搜索后分组数 | 8 |

结论：不必引入虚拟列表。列表按套件折叠，展开最大套件时一次性渲染 230 行仍在 100 ms 量级；搜索用 `useDeferredValue` 让输入保持响应，过滤本身在 50 ms 内完成。v2 在这一页只加了行内预览与健康条：预览是快照阶段切好的 180 字符纯文本（点击才渲染），健康条是一次 `/health` 请求，且只有管理 tab 可见时才发。

## v2 新表面：按需、有界、失败不拖垮别处

| 表面 | 何时取数 | 单次规模上限 | 失败时 |
| --- | --- | --- | --- |
| 健康检查条 | 管理 tab 可见时，一次 `/health` | 7 类 code，最多 6 条可见 + 「还有 N 条」 | 显示读取失败，不挡列表与开关 |
| 内容抽屉 | 用户点开某一行时，一次 `/content` | 256KB / 2 秒预算（模型工具 32KB） | 抽屉内显示错误与重试，列表不动 |
| 洞察趋势 | 切到洞察 tab 时，一次 `/trend` | 最多 120 个点（API 上限 500）；>40 点自动合并为总览分组 | 趋势区显示失败 + 重试，其余卡片照常 |
| 历史回填 | `/trend`、`/stats` 触发的**后台**任务 | 进程内单飞；冷却 60 秒；每轮 ≤8 个会话；单轮预算 6 秒 | 回填失败静默，下一次读再试 |
| 事件时间线 | 切到洞察 tab 时，一次 `/events` | 最多 60 条（文件上限 300，先显示 4 条，可展开） | 显示读取失败 + 重试 |

## 接口延迟（真实实例）

先区分冷读与热读：

- **冷读**（进程刚起、`stats.json` 缓存未命中）：读一次历史文件、按范围聚合后**立即**返回已有行；此时 `coverage.known` 可能为 `null`（后台会话索引还没建好），响应带 `backfilling: true`。
- **热读**（缓存命中、回填冷却中）：只做内存合并，`/trend` 5 ms、`/stats` 22 ms 量级。
- 无论冷热，读取都**不等待** durable-log 回填——回填是后台单飞任务。

稳定路由（5 次采样中位数）：

| 路由 | 中位数 | 响应体 |
| --- | --- | --- |
| `GET /ping` | 1.5 ms | 745 B |
| `GET /summary` | 25.0 ms | 175 KB |
| `GET /locale` | 17.5 ms | 161 KB |
| `GET /health` | 6.6 ms | 647 B |
| `GET /events` | 1.4 ms | 69 B |
| `GET /content`（tools） | 2.1 ms | 697 B |
| `GET /content`（skills） | 5.5 ms | 7.4 KB |

趋势与统计（回填改为后台后的单次探针，671 个会话的语料）：

| 路由 | 实测 | 备注 |
| --- | --- | --- |
| `GET /trend` | 5 ms | 33 个点；首读同样立即返回，`backfilling: true` |
| `GET /stats` | 22 ms | 33 行；`coverage.known` 在后台索引完成前为 `null` |

修复前，`/trend` 与 `/stats` 在每次读取里同步跑 durable-log 回填（8 个会话 / 6 秒），在 671 会话的语料上把一次打开拖到 7.1 s / 2.1 s。2.0.0 把回填改成后台单飞任务（冷却 60 秒、每轮 ≤8 个会话、单轮预算 6 秒），读取只做一次 `stats.json` 读取与内存合并，响应带 `backfilling: true` 让 UI 知道还有数据在路上：打开洞察页的等待从「秒」回到「毫秒」，趋势随后台补齐慢慢变多。

设计原则：

- **一次 tab 切换只发两类请求**（趋势 + 事件），不并发打满；`/health` 只属于管理 tab。
- **所有响应有界**：`/summary` 的条目文本用 180 字符预览，`/content` 有 256KB 上限，趋势点与事件窗口都有数量上限。
- **渲染不重算**：浏览器不算 token、不算预览；行内预览是展开时才渲染的一段文本，长列表仍只画行。
- **抽屉是覆盖层**：打开它不卸载背后的列表，关闭时焦点回到原来的行；搜索在客户端对已取回的文本做高亮，不再发请求。
- **失败隔离**：任一新表面失败只影响自己那块，管理页的开关、设置页的保存都不依赖它们。

## 复现

- 管理页基线：`_research/polish-shots.mjs`（离线夹页，同一份真实快照；会顺带截设置页、深色主题）。
- 三 tab、抽屉、趋势的真实界面：由 `qa` 的临时 profile 实例（`_research/verify/`）截图与探针生成，不碰你的 desktop profile。

如果某天条目涨到四位数或会话历史过万，先看趋势点数（>40 已合并）与列表行数（按套件折叠）；这两个是唯一会随数据线性增长的地方。
